## 11.6 Old update-tracking page vs. the new Projects and Plans system — why the old one shows more detail

User asked why `UserUpdateDashboard.js` (`/my-updates`, the old dedicated update-plan page) shows noticeably more detail for a website-update plan than the same plan does when viewed through the new `ProjectsAndPlans.js` list ("Plans" tab). Both read the exact same order data (`SummaryApi.ordersList`, filtered to `category === 'website_updates'`), so the difference is purely in how much of that data each UI surfaces, not a data/backend gap:

| Aspect | `UserUpdateDashboard.js` (old, dedicated page) | `ProjectsAndPlans.js` "Plans" tab (new, unified list) |
|---|---|---|
| Layout | One dedicated card per plan | One compact row per plan/project, same row shape used for both |
| Updates-remaining | Visual progress bar (blue fill) showing used vs. total updates | Text only: `"{N} update(s) left"` (`getSummaryText()`), no bar |
| Validity/days-left | Visual progress bar (green fill) showing remaining validity | Text only: `"{N} day(s) left"`, no bar |
| Request-update action | Direct "Request Website Update" button on the card itself, disabled automatically once updates are used up or the plan expires | No direct action in the row — opening the row just navigates to `/project-details/:orderId` for more detail |
| Used-up/expired state | Explicit orange warning text explaining *why* ("You've used all your updates" / "Your update plan has expired") | Only a generic "Closed" status badge (`getStatusMeta()`) — no explanation of which condition triggered it |

**Root cause**: `UserUpdateDashboard.js` was purpose-built for exactly one thing — showing a website-update plan's remaining-updates/validity in full detail with an immediate action button — so every pixel on it serves that one job. `ProjectsAndPlans.js` is a generalized list designed to show *both* projects and plans in one consistent row format, so it can only show what fits that shared row shape; plan-specific detail (progress bars, the disabled-state reasoning, the direct action button) doesn't fit a format that also has to represent a project row, so it was left out of the generalized view by design, not by omission or bug. Neither page is "wrong" — they trade off differently between per-item generalized (`ProjectsAndPlans.js`) and single-purpose (`UserUpdateDashboard.js`) at the same click's expense.

## 1. Why this exists

The user asked for a professional, consistent look starting with the customer dashboard, then widened it to the whole site: reduce every font-size in the codebase to a small fixed scale, and reduce text color to a single black/white rule. Before touching any file, a full read-only audit was run to find every current text-size and text-color class in use, so the standardization is evidence-based instead of a guess.

## 2. Approved target type-scale (max 5 sizes)

| Role | Class | Size | Weight | Usage rule |
|---|---|---|---|---|
| H1 | `text-2xl` | 24px | Bold | Page/section main heading |
| H2 | `text-xl` | 20px | Bold | Sub-section heading |
| H3 | `text-lg` | 18px | Semibold | Card/row title |
| Text (default) | `text-base` | 16px | Regular | All normal text — paragraphs, labels, buttons, nav links, table headers — unless it qualifies as sub-text |
| Sub-text | `text-sm` | 14px | Regular | Only when the text is secondary/supporting info under a main line (date under a title, category under a name, etc.) |

No other size class is allowed after this change: `text-xs`, arbitrary bracket sizes (`text-[10px]`, `text-[11px]`, `text-[15px]`, `text-[16px]`, `text-[17px]`), `text-3xl`, `text-4xl`, `text-5xl`, `text-6xl`, and `font-black` are all being removed and mapped into the 5 rows above.

## 3. Approved color rule

- Canonical near-black is **`text-black`** (pure `#000000`) — chosen over the competing `text-slate-950` convention that also existed in the codebase.
- Light background → `text-black`
- Dark background → `text-white`
- All grey-family text colors (`text-gray-400/500/600/700/800/900`, `text-slate-300/400/500/600/700/800/900`) are being removed and mapped to `text-black` or `text-white` depending on the background they sit on (checked per file, not blanket).

## 3.5. Implementation approach decision — why raw Tailwind classes, not a custom class/component

This section records the "how are we writing the code" decision, separate from "what sizes/colors are allowed" (Section 2/3). Kept here so any future session (human or AI) knows this was deliberated, not defaulted into.

### Option considered and rejected: centralized custom class / config token

Idea: define new named font-size tokens in `tailwind.config.js` (e.g. `fontSize: { 'heading-1': '24px', 'body': '16px' }`), or build a shared `components/Typography.js` with wrapper components (`<Heading1>`, `<Text>`, `<SubText>`, etc.), then use those names everywhere instead of raw Tailwind classes.

**Why this was rejected:**
- The codebase (143 files) already writes raw Tailwind utility classes directly on every element — this is the codebase's existing, consistent convention. Introducing a second naming system partway through this project would create two parallel conventions running at once (old raw-class files vs new custom-token files) until every file was migrated, which is itself a new inconsistency risk, not a fix.
- Utility-first is what Tailwind is designed for; wrapping it in named tokens/components fights the framework's own convention rather than using it as intended.
- A custom token hides the actual size behind a name (`text-heading-1` doesn't tell you it's 24px without opening the config), whereas a raw class is self-documenting (`text-2xl` — you know it's 24px on sight). This matters for a small team / future AI sessions picking this project back up without full context.
- The 5-size scale here is small and expected to stay stable (see Section 2) — a central token/config file pays off most when values change often or a multi-brand/multi-theme system is involved. Neither applies here.
- Files already converted (`CustomerDashboard.js`, `DashboardLayout.js`, `ProjectsAndPlans.js`, `CustomerWorkspaceTabs.js`, `StartNewProject.js`, `StartNewProjectDetail.js`, `ProjectDetailView.js`) would all need to be touched a second time to retrofit them into a token system, doubling the work already done for no functional gain.

### Approach adopted: raw Tailwind utility classes, written directly per element, file-by-file

Confirmed with the user as the final approach. Concretely this means:
- Every heading/paragraph/label/button gets its class written directly in its JSX, e.g. `className="text-2xl font-bold text-black"` — no wrapper component, no config-level font-size token.
- The 5-size scale (Section 2) and the black/white rule (Section 3) are the only source of truth for what value goes where; there is no code-level abstraction enforcing it beyond convention and this doc.
- This is the same approach already used for every file completed so far under Section 10 — nothing changes retroactively for those files.

### Rollout: page-by-page, not one whole-site pass

Also confirmed with the user: implementation proceeds one page (or one small group of directly-related files, e.g. a page plus the shared component it renders) at a time — not a single bulk pass across all ~140 remaining files. Reasons:
- The user's standing rule already prohibits blind bulk find-replace and patch work; a whole-site pass in one shot would violate that, since each file needs individual judgment (is this `text-sm` primary body copy or genuine sub-text under a title? is this grey on a light or dark background?) — exactly the kind of case-by-case reasoning Section 8's known risk areas call out.
- Per-file review lets the user visually check each page in the browser before moving to the next, so a mistake (like the letter-spacing/`tracking-[...]` issue found and fixed on `CustomerDashboard.js` and `DashboardLayout.js`) is caught and fixed immediately in the one file it came from, rather than being silently replicated across 140 files first and debugged later.
- Matches the user's existing Understand → Approval → Code → Docs workflow: each file/page is a discrete unit that gets backed up, edited, reviewed, and doc-updated before the next one starts.

## 4. Explicit exemption — status badges/pills

Confirmed by user: the black/white rule applies to normal body text only. Status badges/pills (e.g. "Active Plan", "Payment Rejected", "Completed", "Pending approval") keep their existing semantic colors (green/red/amber/blue/emerald/violet/etc.) so status stays visually distinguishable at a glance. Roughly 230 occurrences across ~70 files fall under this exemption and are NOT part of the black/white conversion.

## 5. Small badge/pill sizes — approved approach

`text-xs`, `text-[10px]`, `text-[11px]` are mostly used on small uppercase tracked badges/pills (rounded-full, tight padding). User approved a direct conversion to `text-sm` across the board rather than a slow per-component visual-QA pass. Any pill/padding breakage this causes will be fixed afterward as a follow-up, not blocked on up front.

Each occurrence needs per-block judgment (does this line sit under a main line as supporting info, or is it the primary text) rather than a blind global rename.
- `text-gray-300` / `text-slate-300` occurrences (`Footer.js`, `WhyChooseSection.js`, `ServiceCard.js`, `ProjectDetails.js`, `AdminDashboard.js`, `AdminFilterDropdown.js`, `ProjectsAndPlans.js`) sit on dark backgrounds and must map to `text-white`, not `text-black` — background context must be checked per occurrence.
